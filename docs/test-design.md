# テスト設計書：SauceDemo（ログイン〜購入）

## 1. 対象と前提

- テスト対象：SauceDemo（https://www.saucedemo.com）の「ログイン → 商品をカートに追加 → 購入完了」までの流れ
- 目的：QAの設計プロセス（要求分析 → テストマップ → FV表 → テストケース → 自動化）を示すポートフォリオ
- 範囲：**機能性**（機能が仕様どおり動くこと。対象はSauceDemo）と、**非機能のうちJMeterで確認できる範囲**（性能・信頼性の一部）。セキュリティ・使用性などは、今回の対象外（「9. 今後の拡張」で扱う）。
- 性能テストの対象：**自分のPC上で動かすアプリ（OWASP Juice Shop）**。SauceDemoは第三者のサイトなので、負荷をかけない。また、フロントエンド中心のアプリとみられ、サーバー側の性能を測る対象に向かない。
- 注意：公式の仕様書がないため、**画面を実際に操作して観察した挙動から推定**している。「要確認」とある箇所は、実装前に手動で確かめて修正する。
- テスト用ユーザー（サイト上に公開されているもの）
  - `standard_user`：通常ユーザー
  - `locked_out_user`：ロックされたユーザー
  - パスワードは共通で `secret_sauce`

## 2. 要求分析（品質目標）

### 2-1. 機能性（SauceDemo）

「どんな品質を目指すか」を、狩野モデルの考え方で3つに分ける。ここで挙げた項目は、FV表の「機能」欄にそのまま記載し、「目的機能」「検証内容」に落とし込む。

対象：ECサイト（SauceDemo）

| あってはならない（Never） | 出来なければならない（Must） | あったらいいな（Want） |
|---|---|---|
| • 誤ったパスワードでログインできる<br><br>• ロックされたユーザーがログインできる<br><br>• 存在しないユーザーがログインできる<br><br>• 未ログインで内部ページを見られる<br><br>• 購入者情報が未入力のまま購入できる<br><br>• 金額が誤って表示される | • ログイン<br><br>• エラーの表示<br><br>• ログアウト<br><br>• 商品一覧の表示<br><br>• カートへの追加<br><br>• カートからの削除<br><br>• 購入<br><br>• 購入手続きの取り消し | • 商品の並び替え<br><br>• 商品詳細の表示 |

（見出しの分類：Never と Must は「当たり前品質」、Want は「魅力的品質」）

- Never と Must は、欠けると「使えない」と感じる品質なので、**テストの優先度は高い**。
- Want は、あると満足度が上がる品質。SauceDemoにすでにある「並び替え」「商品詳細」だけを対象にする。
- 「Never」は、「そうなってはいけない」ことを確かめるので、異常系のテストになる。Never系は考慮から漏れやすいため、先に洗い出している。

### 2-2. 非機能（JMeterで確認できる範囲）

非機能のうち、**JMeterで確認できる範囲**（「速さ・安定性」）の品質目標を、同じ形（Never / Must / Want）で整理する。

#### JMeterで確認できる非機能（ISO/IEC 25010より）

| 品質特性 | 副特性 | JMeterで確認できるか | 今回の扱い |
|---|---|---|---|
| 性能効率性 | 時間効率性（応答時間・スループット） | できる | 対象（NF-01、05〜07） |
| 性能効率性 | 容量満足性（何人まで耐えられるか） | できる | 対象（NF-09、10） |
| 性能効率性 | 資源利用性（CPU・メモリの使用量） | JMeter単体では難しい（サーバー側の監視が別に必要） | 対象外 |
| 信頼性 | 成熟性（通常の負荷でエラーが出ない） | できる（エラー率で確認） | 対象（NF-02、08） |
| 信頼性 | 回復性（負荷のあとに元へ戻る） | できる | 対象（NF-03） |
| 信頼性 | 可用性（長時間動き続ける） | 耐久テストで一部を確認できる | 対象（NF-04） |
| セキュリティ・使用性・互換性など | － | JMeterの対象外 | 対象外（「9. 今後の拡張」） |

対象：自分のPC上で動かすECサイト（OWASP Juice Shop）。ログイン、商品一覧（検索）、カートへの追加の3つのAPIを使う。

| あってはならない（Never） | 出来なければならない（Must） | あったらいいな（Want） |
|---|---|---|
| • ログインの応答が極端に遅い<br><br>• 通常の利用人数でエラーが発生する<br><br>• 負荷をかけたあとに回復しない<br><br>• 長時間の利用で応答が徐々に遅くなる | • ログインが目標時間内に応答する<br><br>• 商品一覧（検索）が目標時間内に応答する<br><br>• カートへの追加が目標時間内に応答する<br><br>• 通常の同時利用で、一連の操作がエラーなく動く | • 負荷が増えても、応答時間の悪化が緩やか<br><br>• 限界（どの人数でエラーが出るか）が分かっている |

**目標値（想定値）**：公式の性能要件（SLA）がないため、自分で決めた仮の値。実測してから見直す。

| 指標 | 目標値（想定） |
|---|---|
| 平均応答時間 | 1秒以内 |
| 95パーセンタイル（95%のリクエストが収まる時間） | 2秒以内 |
| 最大応答時間 | 5秒以内 |
| エラー率 | 1%未満 |

- Juice Shopは、脆弱性を含む練習用アプリなので、**自分のPC上でのみ動かし、外部には公開しない**。
- 他人のサイトや公開サイトには、負荷をかけない。

## 3. テストマップ（機能 × テスト観点）

「機能（縦）」と「テスト観点（横）」の1枚の表で、**実施するテスト**と**実施しないテスト**を、機能性と非機能をまとめて一目で見渡せるようにする。縦は「4. FV表」の目的機能（機能性：FV-01〜19、非機能：NF-01〜10）、横はテスト観点で、各セルの中身は、FV表の Checking / Testing の検証内容から作っている。

- 左の10列（基本動作〜URL直接）は**機能性**のテスト観点（SauceDemoが対象）
- 右の6列（通常負荷〜回復確認）は**非機能**のテスト観点で、JMeterの負荷パターン（Juice Shopが対象）

### 凡例

| 記号 | 意味 |
|---|---|
| ◎ | Checking を実施し、**今回自動化する**（機能性：TC-01〜06 / 非機能：JMeter） |
| ◎+T | Checking は今回JMeterで自動化し、Testing は設計のみ |
| C | Checking を実施する（設計のみ。余裕があれば自動化） |
| T | Testing を実施する（設計のみ。手動で試してから判断） |
| C+T | Checking と Testing の両方を実施する（設計のみ） |
| － | 実施しない |

### テスト観点の定義

#### 機能性（左の10列）

| 観点 | 何を見るか |
|---|---|
| 基本動作 | できる／できない、が仕様どおりか |
| エラー表示 | エラーメッセージが出るか |
| 画面遷移 | 正しい画面に移るか、移らないか |
| 表示内容 | 項目・件数・金額などの表示が正しいか |
| 入力値 | 空・空白・大文字小文字・記号・長い文字列 |
| 繰り返し | 同じ操作の連続・追加と削除の繰り返し |
| 手順変更 | 再ログイン、「戻る」、ページ更新、取消しなど、操作の順序を変える |
| 状態保持 | カートの中身、ログイン状態、並び順が保たれるか |
| 組み合わせ | 複数商品・全商品・複数の入力項目の組み合わせ |
| URL直接 | URLを直接入力してアクセスする |

#### 非機能（右の6列。JMeterの負荷パターン。初期案で、PCの性能に合わせて調整する）

| 観点 | 内容 | 何を見るか |
|---|---|---|
| 通常負荷 | 10同時ユーザー、立ち上げ10秒、1分間 | 目標値を満たすか（基準） |
| 段階的負荷 | 10→20→50→100ユーザーと段階的に増やす（各2分） | 応答時間が悪化し始める人数 |
| ストレス | 限界を超える人数（例：200ユーザー）まで増やす | どう壊れるか（エラーの種類） |
| スパイク | 0→100ユーザーを10秒で立ち上げる | 急な増加への耐性 |
| 耐久 | 10ユーザーで30分続ける | 時間がたつと劣化しないか |
| 回復確認 | 高負荷を止めた直後に、通常のリクエストを送る | 通常の状態に戻るか |

どの負荷パターンでも、応答時間（平均・95パーセンタイル・最大）、エラー率、スループットを記録する。目標値は「2-2. 非機能」の想定値。

### 見方

- **横に見る**：1つの機能に、どの観点のテストを当てるかが分かる。たとえばFV-01は、Checkingで「入れない・エラーが出る・画面が変わらない」を確認し、Testingで「大文字小文字・空白・連続試行」を当てる。NF-01は、通常負荷でログインの応答時間を確認し、段階的負荷で悪化し始める人数を探る。
- **縦に見る**：1つの観点が、どの機能に当たっているかが分かる。たとえば「入力値」は、ログインとチェックアウトの入力欄に集中している。逆に「URL直接」は、FV-04とFV-19にしか当たっておらず、他の画面（カート・購入画面など）に広げる余地がある。非機能では、「通常負荷」に6つの目的機能が集まっており、1本のJMeterプランでまとめて確認できる。
- **Never系**（FV-01〜08、NF-01〜04）は、Checkingで「できないこと」「起きてはいけないこと」を確認し、さらにTestingで条件をぶつける設計にしている。
- **機能性と非機能で、セルが重ならない**：左の10列と右の6列は、別のツール（Playwright / JMeter）、別の対象（SauceDemo / Juice Shop）で実施するため、1行は左右どちらかにだけ記号が入る。

### 実施しないテスト（今回の範囲外）

- 画面の見た目、レイアウト崩れ
- セキュリティ診断（攻撃的な入力による脆弱性の確認）
- 使用性・互換性などの、JMeterで確認できない非機能
- 資源利用性（サーバーのCPU・メモリ使用量。JMeter単体では確認できない）
- 性能のチューニングやボトルネックの調査（計測と記録までを行う）
- すべての入力の組み合わせ（組み合わせ爆発を避け、代表的なものに絞る）
- ブラウザ・端末ごとの互換性の確認（今回はChromiumのみ）
- SauceDemoなど第三者のサイトへの負荷テスト（負荷は自分のPC上のJuice Shopにだけかける）

### 今回の自動化の範囲

- **機能性**：「◎」の6本（TC-01〜06）。ログイン（正常・異常3種）、カート（追加）、チェックアウト（完了）。ツールはPlaywright。
- **非機能**：「通常負荷」の1本のJMeterプラン。NF-01、02、05〜08のChecking（◎、◎+T）を、まとめて計測する。
- **将来の拡張**：「C」「T」は、設計だけ残して、時間が取れたときに追加する。段階的負荷・ストレス・スパイク・耐久・回復確認は、JMeterの負荷パターンを変えて追加する。

## 4. FV表（機能動作確認一覧表）

機能ごとに「何をするための機能か（目的機能）」と「何を確認するか（検証内容）」を整理した表。「機能」欄には、「2. 要求分析」の項目をそのまま記載している（Never → Must → Want の順）。

検証内容は、次の2つの視点に分け、**視点ごとに行を分けて**書いている。自動化のコードの書き方が違うため、行を分けて管理する。

| 視点 | 考え方 | 書き方 |
|---|---|---|
| **Checking** | 仕様どおりに「できること」「できないこと」を確認する。網羅することでモレなく確認する | Must系は「〜できること」、Never系は「〜できないこと」 |
| **Testing** | 誤動作するように、さまざまな条件をぶつけて、バグを叩きに行く | 繰り返し、順序の入れ替え、境界値、空白・大文字小文字・記号など |

FV-IDは、`FV-番号-C`（Checking）、`FV-番号-T`（Testing）の形で、表の上から昇順に振っている。

### 非機能のFV表（JMeterで確認できる範囲）

機能性と同じ形で、JMeterで確認できる非機能（性能効率性・信頼性の一部）を整理する。「機能」欄は、「2-2. 非機能」の Never / Must / Want の項目をそのまま記載している（Never → Must → Want の順）。「品質特性」の列は、「2-2. 非機能」のISO/IEC 25010の表に対応している。

視点の考え方は、機能性と同じ。

| 視点 | 非機能での意味 |
|---|---|
| **Checking** | 目標値（想定値）を満たすかを確認する |
| **Testing** | 限界や極端な条件を試して、どこで悪くなるか・どう壊れるかを探る |

## 6. テストケース（自動化対象の6本）

### TC-01 ログイン成功（FV-09-C, FV-13-C）
- 事前条件：未ログイン
- 手順：ログイン画面を開く → `standard_user` / `secret_sauce` を入力 → ログインを押す
- 期待結果：URLが `/inventory.html`、見出しが「Products」、商品が1件以上表示される

### TC-02 パスワード誤り（FV-01-C）
- 事前条件：未ログイン
- 手順：`standard_user` と誤ったパスワードを入力 → ログインを押す
- 期待結果：エラーが表示される。URLはログイン画面のまま

### TC-03 ユーザー名未入力（FV-10-C）
- 事前条件：未ログイン
- 手順：ユーザー名は空、パスワードのみ入力 → ログインを押す
- 期待結果：ユーザー名が必須である旨のエラーが表示される

### TC-04 ロックされたユーザー（FV-02-C）
- 事前条件：未ログイン
- 手順：`locked_out_user` / `secret_sauce` を入力 → ログインを押す
- 期待結果：ロックされている旨のエラーが表示される。URLはログイン画面のまま

### TC-05 カートに追加（FV-14-C）
- 事前条件：`standard_user` でログイン済み
- 手順：商品「Sauce Labs Backpack」の追加ボタンを押す
- 期待結果：カートのバッジが「1」になり、ボタンの表示が「Remove」に変わる

### TC-06 購入完了（FV-16-C）
- 事前条件：`standard_user` でログイン済み
- 手順：商品を1件追加 → カートへ → Checkout → 名・姓・郵便番号を入力 → Continue → Finish
- 期待結果：購入完了のメッセージ（「Thank you for your order!」）が表示される

### JMeterの実装メモ（非機能）

- テスト対象：自分のPC上のOWASP Juice Shop（`http://localhost:3000`）。**他人のサイトや公開サイトには、負荷をかけない。** Juice Shopは脆弱性を含む練習用アプリなので、外部に公開しない。
- ファイル：`jmeter/load-test.jmx`（テストプラン）、`jmeter/results/`（結果。`.gitignore` に追加する）
- 構成（案）
  - HTTP Request Defaults：サーバー `localhost`、ポート `3000`
  - HTTP Header Manager：`Content-Type: application/json`
  - 準備（setUp Thread Group）：テスト用ユーザーを登録する（`POST /api/Users/`）。ユーザー情報はCSV Data Set Configで読み込む
  - ログイン：`POST /rest/user/login` → JSON Extractorで、認証トークンを取り出す
  - 商品検索：`GET /rest/products/search?q=...`
  - カート追加：`POST /api/BasketItems/`（認証トークンを付ける）
  - Response Assertion：ステータスや、レスポンスの中身を確認する
  - Duration Assertion：目標時間（想定値）を超えたら失敗にする
  - Timer：Uniform Random Timerで、ユーザーごとの待ち時間を入れる
  - Listener：Summary Report、Aggregate Report（95パーセンタイルを見る）。View Results Treeは、動作確認のときだけ使い、負荷をかける実行では無効にする
- 実行：GUIで作り込み、負荷をかける実行は、コマンド（非GUI）で行う。出力先のフォルダは、空か、存在しない状態にしておく。
  `jmeter -n -t jmeter/load-test.jmx -l jmeter/results/result.jtl -e -o jmeter/results/report`
- READMEに、HTMLレポートのスクリーンショットと、目標値との比較を載せる
- エンドポイントやパラメータは、Juice Shopのバージョンで変わることがある。ブラウザの開発者ツール（Networkタブ）で、実際のリクエストを確かめてから作る（要確認）
