# 04. 自動化選定

## 判断基準

| 基準 | 自動化しやすい | 自動化しにくい |
|---|---|---|
| 頻度 | 高頻度で繰り返す | 一度きり |
| 判定明確性 | PASS/FAILを明確化できる | 人の判断に依存する |
| 仕様安定性 | 安定した規則・契約 | 頻繁に変わる |
| 保守コスト | Locator・テストデータを管理できる | 毎回の調整コストが高い |

## 個別の選定

| 対象 | テスト層 | 結論 | 理由 |
|---|---|---|---|
| ログイン正常系 | UI | 自動化 | 主要導線で繰り返し確認するため |
| ログイン入力パターン | API | 自動化 | 組合せが多く、UIより高速・安定して確認できるため |
| 購入主要導線 | UI/E2E | 自動化 | ビジネス上重要なため主要シナリオを回帰する |
| UXの分かりやすさ | 手動 | 手動維持 | 人の判断が必要で自動判定の価値が低い |
| API境界値 | API | 自動化 | 大量のデータ条件を短時間で再実行しやすい |
| 通常負荷 | 性能 | 自動化 | 基準値を継続比較し劣化を把握する |
| 探索的テスト | 手動 | 手動維持 | 仮説を変えて探索するため固定スクリプト化に向かない |

現行リポジトリではログイン・カート・チェックアウトのUI、JSONPlaceholder API、JMeter負荷テストを実装済みとみなす。アクセシビリティと夜間クロスブラウザは未実装である。
